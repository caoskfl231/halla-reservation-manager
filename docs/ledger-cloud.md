# 로그인과 공용 장부

GitHub Pages는 화면을 제공하고 Supabase는 로그인 및 공용 장부를 보관한다.
장부 DB는 주문 DB와 별도인 비공개 halla_ledger_private 스키마에 있다.
기존 승인된 주문 관리자만 초기 owner가 되고, 일반 Auth 가입은 장부 접근 권한을 만들지 않는다.
TOTP가 설정된 계정은 서버에서 aal2를 요구한다.

## 사용자 추가

Supabase Authentication에서 새 계정을 만든 뒤 정확한 이메일로 권한을 부여한다.
회원가입만으로는 접근할 수 없다. 사용자 확인 후 아래 SQL을 실행한다.

```sql
insert into halla_ledger_private.members(user_id, role)
select id, 'editor' from auth.users
where lower(email) = lower('확인된 사용자 이메일')
  and email_confirmed_at is not null and is_anonymous is not true
on conflict (user_id) do update set role = 'editor';
```

## 기존 자료 이전

첫 owner 로그인 후 '백업 파일 선택' 또는 '이 PC의 자료 옮기기'를 사용한다.
이 PC의 자료는 IndexedDB hallapa_db에서 읽으며 기존 데이터는 지우지 않는다.
서버 revision=0일 때만 최초 자료 이전이 허용된다.
백업 JSON의 meta.dbName과 키를 검증하며 기본값으로 기존 자료를 덮어쓰지 않는다.

## 자동백업과 복구

postgres 소유의 halla-ledger-daily-backup Cron 작업이 매일 18:00 UTC
(한국 시간 다음 날 03:00)에 공용 장부 스냅샷을 보관한다. 최근 30일분을 유지한다.
첫 자료 이전 직후에도 백업을 만들며, 당일 정기 백업이 이를 대체한다.
revision=0인 빈 장부는 백업하지 않는다. 화면이 닫혀 있어도 서버에서 실행한다.
홈 상단 '자동백업'에서 날짜별 JSON 내려받기가 가능하고 owner는 전체 복구할 수 있다.
전체 복구는 기존 revision 검증과 복구 전 restore_history 보관을 그대로 사용한다.
하루 중 백업 시각 이후 기록은 그날 백업에 포함되지 않으므로 중요한 작업 뒤에는
전체백업 파일도 따로 보관한다. 이 백업은 같은 데이터베이스 안의 논리적 복사본이며
Supabase 프로젝트 자체 삭제나 장애에 대한 외부 백업을 대체하지 않는다.
관련 스키마·Cron 설정은 ledger-backups.sql에 있다.

## 거래별 저장

일반 수정은 변경된 거래·거래처·품목 등의 기록만 부분 저장한다. 기록마다 버전을
확인하므로 다른 거래를 동시에 저장해도 덮어쓰지 않는다. 같은 기록이 먼저 변경되면
충돌을 안내하고 해당 저장을 취소한다. 한 DB 함수가 변경한 여러 기록은 함께 저장하거나
함께 취소한다. 신규 거래의 숫자 ID는 서버에서 발급한다.

다른 기록 저장 후에도 화면에 남은 기록의 이전 버전을 유지해 오래된 수정이 승인되지
않게 한다. 삭제된 기록의 버전도 보관한다. 저장 응답을 받은 후에만 완료를 표시한다.
응답이 유실되면 자동 재전송하지 않고 '최신 불러오기'로 결과를 확인하게 한다.
전체 가져오기·복구는 장부 전체 revision을 확인하며, 복구 전 스냅샷은 restore_history에 남는다.
서버는 호환용 스냅샷도 유지하므로 이전 클라이언트의 전체 저장 역시 기록 버전에 반영된다.
초기 스키마는 ledger-cloud-schema.sql, 거래별 저장 확장은 ledger-records.sql 순서로 적용한다.

각 페이지는 독립적인 임시 IndexedDB에 로그인 후 받은 자료를 적재한다.
기존 장부 모듈의 계산과 정규화는 유지한다. 페이지를 닫으면 임시 DB를 정리한다.
다른 기기의 변경 여부를 15초마다 확인하며 작성 중인 화면을 자동으로 새로고침하지 않는다.
사용자가 '최신 불러오기'를 눌러 반영한다.

오프라인 편집·자동 병합은 제공하지 않는다. 전체 스냅샷은 최대 25MB로 제한된다.
기존 UI의 한 동작이 DB 함수를 여러 번 호출하면 각 호출이 개별 서버 저장이다.
부분 저장은 서버에서 짧은 장부 잠금으로 직렬화하며 매번 호환용 스냅샷을 재구성한다.
대규모 장부에서는 조회도 개별 기록 API로 확장할 수 있다.
로그인 토큰은 주문페이지와 다른 sessionStorage 키를 사용하며 비밀번호는 저장하지 않는다.

# 로그인과 공용 장부

GitHub Pages는 화면을 제공하고 Supabase는 로그인 및 공용 장부를 보관한다.
장부 DB는 주문 DB와 별도인 비공개 halla_ledger_private 스키마에 있다.
기존 승인된 주문 관리자만 초기 owner가 되고, 일반 Auth 가입은 장부 접근 권한을 만들지 않는다.
TOTP가 설정된 계정은 서버에서 aal2를 요구한다.

## 거래 저장 속도 개선 (2026-10-10)

`ledger-fast-save.sql` 적용 후 비공개 `records`가 현재 장부의 기준이다.
일반 저장은 변경된 행과 revision만 원자적으로 갱신한다. `state.snapshot`은 마지막 전체 가져오기/구형 저장의 캐시이며 현재 장부로 직접 읽으면 안 된다.
전체 자료는 내부 STABLE `current_snapshot()`으로 재구성한다. 로그인·최신 불러오기, 03시 자동백업, 전체 복구 전 원본 보존이 모두 이 경로를 사용한다.
`payload_bytes` 생성 열로 전체 장부를 직렬화하지 않고 동일한 25MB 제한을 검사한다. 구형 저장/복구 RPC와도 호환되며, 회원·MFA·행 버전 검사는 유지한다.
클라이언트의 거래 추가/수정/삭제/전표 일괄 저장은 해당 IndexedDB 행만 읽고 변경 목록을 보낸다. 전체 내보내기/전체 비교를 하지 않는다. 신규 전표 번호는 한 요청으로 예약한다.
저장 확인을 받은 뒤에만 완료 표시한다. 응답이 유실되면 자동 재시도하지 않고 최신 불러오기로 결과를 확인한다.

## 사용자 추가

Supabase Authentication에서 새 계정을 만든 뒤 정확한 이메일로 권한을 부여한다.
회원가입만으로는 접근할 수 없다. 사용자 확인 후 아래 SQL을 실행한다.

```sql
insert into halla_ledger_private.members(user_id, role)
select id, 'editor' from auth.users
where lower(email) = lower('확인된 사용자 이메일')
  and email_confirmed_at is not null and is_anonymous is not true
on conflict (user_id) do update set role = 'editor';
```

## 기존 자료 이전

sales_quotes 항목도 보존한다. 임시 계산 DB에는 id 키를 쓰는 해당 스토어가 포함되며
화면에서 사용하지 않는 자료라도 전체백업 및 서버 저장에서 제외하지 않는다.
큰 자료의 서버 이전은 집합 기반 SQL로 처리하고 전체 저장 요청의 응답 대기는 최대 120초다.
시간 초과는 실패가 확정된 것이 아니라 저장 결과가 불확실한 상태이므로 최신 불러오기로
결과를 확인하고 자동 재전송하지 않는다. 추가 설정은 ledger-import-fix.sql을 참고한다.

첫 owner 로그인 후 '백업 파일 선택' 또는 '이 PC의 자료 옮기기'를 사용한다.
이 PC의 자료는 IndexedDB hallapa_db에서 읽으며 기존 데이터는 지우지 않는다.
서버 revision=0일 때만 최초 자료 이전이 허용된다.
백업 JSON의 meta.dbName과 키를 검증하며 기본값으로 기존 자료를 덮어쓰지 않는다.

## 자동백업과 복구

postgres 소유의 halla-ledger-daily-backup Cron 작업이 매일 18:00 UTC
(한국 시간 다음 날 03:00)에 공용 장부 스냅샷을 보관한다. 최근 30일분을 유지한다.
첫 자료 이전 직후에도 백업을 만들며, 당일 정기 백업이 이를 대체한다.
revision=0인 빈 장부는 백업하지 않는다. 화면이 닫혀 있어도 서버에서 실행한다.
홈 상단 '자동백업'에서 날짜별 JSON 내려받기가 가능하고 owner는 전체 복구할 수 있다.
전체 복구는 기존 revision 검증과 복구 전 restore_history 보관을 그대로 사용한다.
하루 중 백업 시각 이후 기록은 그날 백업에 포함되지 않으므로 중요한 작업 뒤에는
전체백업 파일도 따로 보관한다. 이 백업은 같은 데이터베이스 안의 논리적 복사본이며
Supabase 프로젝트 자체 삭제나 장애에 대한 외부 백업을 대체하지 않는다.
관련 스키마·Cron 설정은 ledger-backups.sql에 있다.

## 거래별 저장

적용 후 기록을 수정·삭제하면 record_history에 변경 직전 내용을 같은 DB 트랜잭션으로
보관한다. 실패한 저장은 변경과 이력이 함께 롤백된다. 전체 복구로 바뀐 기록도 보관한다.
홈 '수정·삭제 기록'에서 이전 내용을 확인하고 owner가 해당 기록 하나를 복구할 수 있다.
확인한 이후 현재 버전이 달라졌으면 복구를 거절한다. 복구 자체로 바뀐 현재 내용도 이력에 남는다.
목록은 시간과 UUID 복합 커서로 50개씩 조회하며 이력은 자동 삭제하지 않는다.
하나의 동작이 여러 기록을 바꾼 경우 개별 복구 후 관련 기록도 확인해야 한다.
같은 DB 안의 이력 보관이며 프로젝트 삭제·DB 장애를 위한 외부 백업은 아니다.
적용 이전에 사라진 자료를 복원하거나 인터넷에 저장되지 않은 입력을 보관하지는 않는다.
설정은 ledger-history.sql을 참고한다.

일반 수정은 변경된 거래·거래처·품목 등의 기록만 부분 저장한다. 기록마다 버전을
확인하므로 다른 거래를 동시에 저장해도 덮어쓰지 않는다. 같은 기록이 먼저 변경되면
충돌을 안내하고 해당 저장을 취소한다. 한 DB 함수가 변경한 여러 기록은 함께 저장하거나
함께 취소한다. 신규 거래의 숫자 ID는 서버에서 발급한다.

다른 기록 저장 후에도 화면에 남은 기록의 이전 버전을 유지해 오래된 수정이 승인되지
않게 한다. 삭제된 기록의 버전도 보관한다. 저장 응답을 받은 후에만 완료를 표시한다.
응답이 유실되면 자동 재전송하지 않고 '최신 불러오기'로 결과를 확인하게 한다.
전체 가져오기·복구는 장부 전체 revision을 확인하며, 복구 전 스냅샷은 restore_history에 남는다.
서버는 호환용 스냅샷도 유지하므로 이전 클라이언트의 전체 저장 역시 기록 버전에 반영된다.
초기 스키마는 ledger-cloud-schema.sql, 거래별 저장 확장은 ledger-records.sql 순서로 적용한다.

각 페이지는 독립적인 임시 IndexedDB에 로그인 후 받은 자료를 적재한다.
기존 장부 모듈의 계산과 정규화는 유지한다. 페이지를 닫으면 임시 DB를 정리한다.
다른 기기의 변경 여부를 15초마다 확인하며 작성 중인 화면을 자동으로 새로고침하지 않는다.
사용자가 '최신 불러오기'를 눌러 반영한다.

오프라인 편집·자동 병합은 제공하지 않는다. 전체 스냅샷은 최대 25MB로 제한된다.
기존 UI의 한 동작이 DB 함수를 여러 번 호출하면 각 호출이 개별 서버 저장이다.
부분 저장은 서버에서 짧은 장부 잠금으로 직렬화하며 매번 호환용 스냅샷을 재구성한다.
대규모 장부에서는 조회도 개별 기록 API로 확장할 수 있다.
로그인 토큰은 주문페이지와 다른 전용 키를 사용하며 비밀번호는 저장하지 않는다. 기본 로그인은 sessionStorage에 보관한다. 로그인 화면의 '자동 로그인'을 선택하면 비밀번호 인증, 필요한 2단계 인증 및 장부 권한 확인이 모두 끝난 뒤 localStorage로 옮겨 같은 브라우저를 다시 열어도 인증 상태를 이어간다. 토큰 갱신도 선택한 저장 방식을 유지하며 일시적인 네트워크 오류만으로 로그인 정보를 지우지 않는다.

'아이디 저장'은 이메일만 별도 보관하는 독립 옵션이다. 로그아웃은 두 저장소의 로그인 토큰을 즉시 지우고 진행 중인 갱신 응답이 로그인을 되살리지 못하게 한다. 저장한 아이디는 로그아웃 후에도 남으며 체크를 해제하면 지워진다. 자동 로그인은 개인 기기에서만 선택한다. 브라우저 데이터 삭제, 서버의 세션 취소 또는 보안 정책에 따른 만료 시에는 다시 로그인해야 한다.
# 분할 백업 가져오기 (2026-10-10)

전체복구와 최초 가져오기는 `cloud-import.js`를 통해 200행/약180KB 이하 묶음으로 보냅니다. 서버는 별도 비공개 임시 테이블에서 코드·개수·중복을 검사합니다. 중단된 전송은 현재 장부를 바꾸지 않습니다. 모든 묶음이 도착한 뒤, 원래 장부 버전이 그대로일 때에만 한 트랜잭션으로 반영합니다. 복구 전 장부와 변경·삭제 이력, 최초 자동백업도 같은 트랜잭션에서 보존됩니다.

최종 반영 RPC만 최대60초의 함수별 DB 제한을 사용합니다. 일반 로그인·조회·저장 권한과 역할별 제한은 바꾸지 않습니다. 중복 묶음과 최종 반영에는 재실행 검사를 넣었지만 브라우저는 네트워크 오류 시 자동 재전송하지 않습니다. 응답이 유실되면 최신 불러오기로 결과를 확인해야 합니다. 임시 전송은 24시간 뒤 만료되며 다음 가져오기 시작 시 해당 사용자의 만료된 임시 자료만 제거됩니다. 완료된 자료의 임시 행은 즉시 제거하고 짧은 완료 영수증만 유지합니다.

15초마다 전체 장부를 내려받던 갱신 확인은 작은 버전 조회 RPC로 변경했습니다. 입력 중인 화면에는 다른 기기의 자료를 자동 덮어쓰지 않습니다.
